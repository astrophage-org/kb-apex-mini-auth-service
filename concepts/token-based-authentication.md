# Token-Based Authentication

**Token-Based Authentication** in `mini-auth-service` is an identity verification and access management pattern utilizing cryptographically signed, stateless **JSON Web Tokens (JWT)**. Instead of retaining session state in a server-side cache or database, all identity context and access permissions are encapsulated directly within the token passed between the client and the application.

This document describes the stateless authentication architecture, token claim structure, and the end-to-end token lifecycle implemented across the [[entities/api-router]], [[entities/auth-engine]], and [[entities/settings]].

---

## 1. Stateless Authentication Model

In traditional stateful authentication, a server issues an opaque session ID stored in a database or distributed cache (e.g., Redis). Every subsequent request requires a database lookup to validate the session ID and resolve user identity.

`mini-auth-service` adopts a **stateless architecture** using RFC 7519 JSON Web Tokens:
- **Self-Contained Identity**: Identity information is stored in the token payload itself.
- **Decentralized Verification**: Verification requires only the shared secret and algorithm specified in [[entities/settings]], eliminating database I/O on protected endpoints.
- **Horizontal Scalability**: Stateless API instances can independently verify tokens without requiring session sharing or sticky routing.

For architectural trade-offs, see [[decisions/stateless-vs-stateful-sessions]].

```
+--------+                    +------------------------------------+
|        |-- 1. POST /login ->| API Router (`src/main.py`)         |
|        |   (form data)      | - Validates credentials via        |
|        |                    |   [[entities/auth-engine]]         |
|        |<-- 2. JWT Token ---| - Issues signed Bearer token       |
| Client |                    +------------------------------------+
|        |
|        |                    +------------------------------------+
|        |-- 3. GET /me ----->| API Router (`src/main.py`)         |
|        |   (Bearer Token)   | - Injects `verify_token` via DI    |
|        |                    | - Decodes & verifies signature     |
|        |<-- 4. User Data ---| - Serves payload without DB query  |
+--------+                    +------------------------------------+
```

## 2. JWT Structure & Claims

A JSON Web Token consists of three base64url-encoded components separated by dots (`.`): `Header.Payload.Signature`.

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJhZG1pbiIsImV4cCI6MTcxODAwMDAwMH0.signature...
\__________________________________/ \________________________________________/ \__________/
              Header                                  Payload                     Signature
```

### A. Header
The header defines the token metadata, including the token type and cryptographic algorithm:
```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```
The algorithm is dynamically configured via `settings.ALGORITHM` (default: `HS256`). See [[concepts/jwt-signing-verification]] and [[decisions/symmetric-vs-asymmetric-signing]].

### B. Payload (Claims)
The payload contains the **claims**—statements about the entity (subject) and metadata about the token itself. For the exact schema, see [[entities/jwt-token-payload]].

| Claim | Type | Description | Source |
| :--- | :--- | :--- | :--- |
| `sub` | `string` | **Subject**: The unique identifier/username of the authenticated user. | `user["username"]` from `authenticate_user()` |
| `exp` | `integer` (Unix Epoch) | **Expiration Time**: The precise timestamp after which the token is invalid. | Current UTC time + `expires_delta` (default: 15 min) |

Example payload decoded:
```json
{
  "sub": "admin",
  "exp": 1718000900
}
```

### C. Signature
The signature is generated by hashing the encoded header and payload using the secret key specified in `settings.JWT_SECRET`:
$$\text{Signature} = \text{HMAC-SHA256}(\text{base64Url}(Header) + "." + \text{base64Url}(Payload), \text{JWT\_SECRET})$$

## 3. Token Lifecycle

The lifecycle of an access token spans four distinct phases: issuance, transport, verification, and expiration.

```
       [ Client ]              [ Auth Engine / Router ]
           |                              |
[Phase 1]  |-- POST /login (Creds) ------>|
(Issuance) |                              |-- authenticate_user()
           |                              |-- create_access_token()
           |<-- { access_token, bearer } -|
           |                              |
[Phase 2]  |  [ Token Stored Locally ]    |
(Transport)|                              |
           |                              |
[Phase 3]  |-- GET /me (Token) ---------->|
(Verify)   |                              |-- verify_token()
           |                              |-- Decodes & checks `exp`
           |<-- 200 OK { username } ------|
           |                              |
[Phase 4]  |-- GET /me (Expired Token) -->|
(Expiry)   |                              |-- verify_token() fails
           |<-- 401 Unauthorized ---------|
```

### Phase 1: Issuance & Creation
1. The client submits credentials via `POST /api/v1/auth/login` as documented in [[summaries/api-endpoints]].
2. The credential validation flow executes (see [[concepts/credential-validation-flow]]).
3. Upon successful validation, the [[entities/auth-engine]] calls `create_access_token()`:
   ```python
   def create_access_token(data: dict, expires_delta: timedelta = None):
       to_encode = data.copy()
       expire = datetime.utcnow() + (expires_delta or timedelta(minutes=15))
       to_encode.update({"exp": expire})
       return jwt.encode(to_encode, settings.JWT_SECRET, algorithm=settings.ALGORITHM)
   ```
4. The signed token is returned in a standard OAuth2-compliant response:
   ```json
   {
     "access_token": "eyJhbGciOi...",
     "token_type": "bearer"
   }
   ```

### Phase 2: Client Storage & Transport
The client stores the token (e.g., in memory or secure storage) and provides it on subsequent requests to protected endpoints.

### Phase 3: Verification & Decoding
When a protected route is requested (such as `GET /api/v1/auth/me`), FastAPI resolves the `verify_token` dependency via [[concepts/dependency-injection]]:
```python
def verify_token(token: str):
    try:
        payload = jwt.decode(token, settings.JWT_SECRET, algorithms=[settings.ALGORITHM])
        return payload
    except Exception:
        return None
```
PyJWT verifies:
1. **Cryptographic Integrity**: The signature matches the payload and header using `settings.JWT_SECRET`.
2. **Algorithm Consistency**: The token header matches `settings.ALGORITHM`.
3. **Temporal Validity**: The current UTC time is strictly less than the `exp` claim.

### Phase 4: Expiration & Invalidation
Tokens are short-lived (TTL of 15 minutes). Once `datetime.utcnow() > payload["exp"]`, `jwt.decode()` raises `jwt.ExpiredSignatureError`. The `verify_token()` function catches the exception and returns `None`, prompting the [[entities/api-router]] to reject the request with HTTP `401 Unauthorized`.

## 4. Architectural Relationships

- **Configuration Binding**: Token generation and verification directly depend on the [[entities/settings]] singleton (`JWT_SECRET`, `ALGORITHM`).
- **Dependency Injection**: Route handlers in [[entities/api-router]] do not manually parse tokens; they rely on FastAPI dependencies (`Depends(verify_token)`), detailed in [[concepts/dependency-injection]].
- **Cryptographic Details**: For in-depth signing mechanics and error handling, see [[concepts/jwt-signing-verification]].
- **High-Level Flow**: See [[summaries/architecture-overview]] for how token-based authentication fits into the overall system architecture.

# Business requirement: Hashing login tokens for downstream services

## The request
> "The login token has to be hashed before being sent to the downstream services"

## Problem
In the current authentication flow of the **mini-auth-service**, tokens generated during user authentication (such as via the `/api/v1/auth/login` endpoint documented in [[kb:mini-auth-service/summaries/api-reference]]) are handled in their raw, signed form. When downstream services receive or store raw login tokens, any logging, intermediary cache, or service compromise poses a risk of exposing active bearer credentials. Hashing the token before forwarding or dispatching it downstream mitigates the blast radius of potential credential leaks across internal systems.

## Who is affected
- **Downstream consuming services**: Any internal application or microservice downstream of `mini-auth-service` that receives session or token references.
- **End users**: Protected against token compromise if a downstream service's logs or datastores are exposed.
- **Security & Compliance teams**: Ensures adherence to least-privilege credential sharing and secure token lifecycle practices.

## What should change
- When login tokens generated by `mini-auth-service` ([[kb:mini-auth-service/entities/presentation-main]]) are sent to or consumed by downstream services, a hashed version of the token must be transmitted rather than the raw, unhashed token.
- Downstream service interfaces and communication channels must accept and process the hashed token representation for subsequent operations.

## What "done" looks like
Any downstream service interacting with the login flow receives only a cryptographically hashed representation of the login token. Raw login tokens are never forwarded across downstream service boundaries.

## Examples
- **Login token dispatch**: When a client authenticates via `POST /api/v1/auth/login` ([[kb:mini-auth-service/summaries/api-reference]]), the generated access token is securely hashed before being propagated to downstream event listeners or downstream services.
- **Downstream auditing/session tracking**: Downstream services requiring token reference or validation rely on the hashed value rather than inspecting or storing the raw JWT.

## Verification checklist
- [ ] Downstream services receive only the hashed token instead of the raw login token.
- [ ] User login and downstream service workflows continue to function successfully with the hashed token representation.
- [ ] No unhashed login tokens are emitted in downstream network calls or logs.
- [ ] The login token is hashed before being sent to downstream services.

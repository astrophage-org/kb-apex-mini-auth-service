# Product spec: Downstream Login Token Hashing

## Goal
Protect bearer credentials across internal architectures by ensuring that all login tokens generated by `mini-auth-service` are cryptographically hashed prior to being sent to or consumed by downstream services.

## User stories
- **As a downstream service consumer**, I want to receive a hashed representation of the login token instead of the raw JWT, so that downstream datastores, caches, and logs do not store active bearer credentials.
- **As a security engineer**, I want login token payloads forwarded across downstream service boundaries to be hashed, so that a compromise in downstream infrastructure does not expose reusable user access tokens.
- **As an API client**, I want to authenticate via `POST /api/v1/auth/login` ([[kb:mini-auth-service/summaries/api-reference]]) and continue receiving standard token credentials for client-level requests without breaking existing API contracts.

## Acceptance criteria
- **AC-1: Hashing tokens for downstream dispatch**
  - **Given** a client successfully authenticates via `POST /api/v1/auth/login` ([[kb:mini-auth-service/summaries/api-reference]]) handled by `src/main.py` ([[kb:mini-auth-service/entities/presentation-main]]),
  - **When** the authentication event or token reference is dispatched to downstream services,
  - **Then** the dispatched payload must contain the cryptographically hashed token instead of the raw, unhashed JWT string.
- **AC-2: Prevention of raw token leakage downstream**
  - **Given** any downstream communication initiated during the login lifecycle,
  - **When** downstream network payloads, events, or service calls are inspected,
  - **Then** no raw JWT or unhashed token strings are emitted across the downstream integration boundaries.
- **AC-3: Client API contract continuity**
  - **Given** a client authenticating via `POST /api/v1/auth/login` ([[kb:mini-auth-service/summaries/api-reference]]),
  - **When** the HTTP response is returned to the client caller,
  - **Then** the client receives the standard bearer access token required to access protected routes such as `GET /api/v1/auth/me` ([[kb:mini-auth-service/decisions/fastapi-dependency-injection]]).

## Edge cases
- **Shared secret exposure *(from the map)*:** Consuming downstream services that only require token tracking or session mapping must not require access to `JWT_SECRET` ([[kb:mini-auth-service/decisions/jwt-hs256-signing]]), using the hashed token identifier instead.
- **High-frequency / duplicate logins:** When identical or rapid repeated logins occur for the same user account (e.g., `admin`), downstream services must receive distinct hashed tokens corresponding to each uniquely signed JWT timestamp.
- **Malformed or empty token state:** If token generation fails or encounters an unparseable state, downstream dispatch must fail safely without emitting null or unhashed fallback strings.

## Out of scope
- Modifying client-facing response schemas for `POST /api/v1/auth/login` or `POST /auth/login` ([[kb:mini-auth-service/summaries/api-reference]]).
- Modifying the core route guard validation logic in `GET /api/v1/auth/me` ([[kb:mini-auth-service/decisions/fastapi-dependency-injection]]).
- Implementing dynamic secret management or persistent user databases described in the roadmap ([[kb:mini-auth-service/summaries/roadmap-and-improvements]]).

## Success metric
- 100% of login token events and messages delivered to downstream services contain only hashed token representations, with 0 raw JWTs exposed in downstream logs or interfaces.

## Priority
**P2** — High priority security enhancement to eliminate credential leakage across internal service boundaries and reduce the blast radius of potential downstream log or data compromises.

## Verification checklist
- [ ] AC-1: Downstream dispatch receives a cryptographically hashed token rather than the raw JWT upon login via `POST /api/v1/auth/login`.
- [ ] AC-2: No raw, unhashed JWTs are emitted in downstream network calls, logs, or downstream message bodies.
- [ ] AC-3: Client-facing API responses for `POST /api/v1/auth/login` continue to provide valid bearer tokens compatible with `GET /api/v1/auth/me`.
- [ ] Edge Case: Consuming downstream services do not require access to `JWT_SECRET` to handle token references.
- [ ] Edge Case: Consecutive login events generate distinct, valid hashed tokens downstream.
- [ ] Edge Case: Malformed or empty token conditions fail safely without emitting raw values downstream.
- [ ] Success Metric: 100% of login token payloads sent downstream are hashed with zero raw JWT exposures.
